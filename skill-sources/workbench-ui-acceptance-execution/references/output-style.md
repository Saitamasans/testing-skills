# 输出风格

## 聊天摘要

聊天回复是给产品、测试负责人或业务方快速判断结果用的，不要写成流水账。必须先给结论，再给数字、关键验证点、风险/阻塞和报告位置。

必须尽量贴近下面的结构和语气，不要自行改成“总结型口吻”：

```md
验收完成 ✅

需求 #{需求编号} 【{优先级}】 {需求名称} 已在 {测试环境} 完成验收，报告已生成。

📊 测试结果：{通过数}/{总已执行数} 通过，{待确认/阻塞数} 待确认，{不通过数} 不通过

| 状态 | 数量 | 说明 |
|---|---:|---|
| ✅ 通过 | {通过数} | 核心 UI 全部到位 |
| ⚠️ 待确认 | {待确认数} | 缺账号、权限、数据或口径，未强行脑补 |
| ❌ 不通过 | {不通过数} | — |

🔑 已验证的关键点
- {模块/页面}：{已验证事实 1}
- {模块/页面}：{已验证事实 2}
- {模块/页面}：{已验证事实 3}
- {模块/页面}：{已验证事实 4}
- {模块/页面}：{已验证事实 5}

⚠️ 上线前建议补充验证
1. {待补充验证 1}
2. {待补充验证 2}
3. {待补充验证 3}
4. {待补充验证 4}

报告文件和 {截图数} 张截图已生成，可以直接查看。
```

聊天输出规则：

- 不只写“测试通过/正常”，必须说明通过了什么、没测什么、为什么没测。
- 有不通过时标题必须明确写“不通过”或“存在不通过项”，不要用“基本通过”弱化风险。
- 有阻塞时要把阻塞归类，例如缺账号、缺权限、缺数据、验证码、测试桩缺失、口径冲突。
- 允许少量 emoji 作为状态标识，控制在结论、统计、关键点标题和状态列中。
- 报告路径或附件说明必须放在聊天回复末尾，方便用户直接打开。
- 不要把“预览图”当成交付物去提示用户；预览图只用于内部自检。

## HTML 视觉风格

HTML 报告应像产品经理截图里的验收报告：首屏能看懂结果，正文能追证据，整体克制但不死板。

- 使用白底、浅灰页面背景、轻阴影卡片和清晰表格。
- 顶部必须有结论横幅：绿色表示全部通过，黄色表示有待确认/阻塞但无失败，红色表示存在不通过。
- 首屏必须包含：任务名、环境、执行方式、结论、通过/不通过/待定/阻塞统计。
- 统计卡片使用大数字，颜色区分通过、待定、失败、截图。
- 主表优先展示可执行用例；阻塞/待定项可以单独分区，避免大量未执行用例淹没已验证结论。
- 表格行可对通过用例使用浅绿色背景，阻塞/待定用浅黄色，失败用浅红色。
- 长文本要保留但不能撑爆页面；可使用换行、摘要、详情列或横向滚动。
- 证据截图使用两列或自适应网格，图片有边框和说明文字。
- 允许少量 emoji 表达状态，但不要用过多装饰。
- 不使用营销式 hero，不使用花哨背景，不依赖外部字体或 CDN。

## HTML 字段要求

报告至少展示：

- 任务名称
- 测试环境
- 执行方式
- 执行时间
- 通过/不通过/待定/阻塞数量
- 逐用例结果和实际结果摘要
- 阻塞原因
- 截图索引
- 最终验收结论

## 最终结论口径

- `全部通过`：无不通过、无待定、无阻塞。
- `补充验证完成，全部通过`：用户要求补测的范围已全部通过，但历史范围存在已说明的非本轮事项。
- `部分通过，存在阻塞项`：无不通过，但因账号、权限、数据、验证码、环境或口径导致部分用例不能执行。
- `存在不通过项`：任一用例出现明确偏差且可复现。
- `待确认`：预期与页面现状、需求口径或用例描述冲突，无法直接判定缺陷。
