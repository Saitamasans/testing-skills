# 测试地图交付规范

默认交付聊天摘要、自包含 HTML 主报告和完整 Word 报告。三者共享同一分析底稿与证据，Word 不是聊天摘要的复制版。使用宿主已有工具；生成受阻时先尝试受支持替代方式，再明确缺失附件，不能把 Markdown 改扩展名冒充 Word，也不能称全部交付完成。不启用旧 Runtime。

HTML 应离线可读，样式和必要图片内嵌，不依赖远程 CDN、分析脚本或自动联网。Word 使用真正 .docx，生成后检查内容一致性及渲染后的表格、分页和图片。所有文件仅保存本地，并在聊天中给出实际文件链接。

聊天摘要顺序：完成程度（受限时置顶）→ 系统定位 → 关键发现 → 有依据的测试重点和优先级 → 缺口 → HTML/Word 链接。语气专业直接，不堆术语，也不过度口语化。

## 用户先看结果

主报告默认使用：这是什么系统/模块；有哪些已确认功能；功能关系和限制（区分确认与推测）；优先测什么及为什么；哪些没看清。证据索引和技术数据放后面，用户无需理解内部字段才能使用结果。下面六部分是证据底稿，不要求原样铺在聊天首页。

有效测试建议示例：“页面分别有账号余额与收益余额，所以要确认操作影响哪个账户，是否误改另一项”；这是假设性测试建议，不是已发现账务错误。无效示例：“应进行功能、性能、安全测试”。

按钮文案含混时，优先结合已读的确认提示/绑定代码解释意图，并明确没有验证后端。例如“重置提现”对应“重置今日提现次数”，只能证明前端表达的意图，不证明服务端实际只改次数。不同模块共有用户/房主/群主字段仅形成关联线索，不能声称已验证同一账号的全链路关系。

## 证据底稿六部分

1. 范围与能力：环境、账号范围（不含认证凭据）、起止点、已验证能力、连接异常、完成程度。
2. 系统地图：模块→菜单/页面→代表性详情；关联 route、parent_id、状态与 evidence_ids。
3. JS 技术地图：资产优先级、已读范围、路由/函数/接口声明；外部正文缺失列清楚。
4. 代表性链：入口证据、条件分支、方法/路径模板、结果反馈、未知边界。每条链独立停止原因。
5. 测试认知：权限/状态线索、风险、验证问题、测试建议；不声称已执行或已证明漏洞。
6. 覆盖与证据：visited/skipped/blocked、未解析项、动态内容限制、请求计量是否可用。

默认不生成大量详细测试用例，也不执行业务测试。用户要求时才生成详细用例或 Excel。Excel 可投影五张表：系统地图、调用链、风险与验证、批次覆盖、证据索引；不能为了填满表格制造内容。所有格式来自同一 run_id。

## 关联字段

实体 id、source/locator、evidence_ids、status（observed/static/inferred/unverified）、limitations。调用链加 nodes/edges/condition/outcome/stop_reason；不可把互斥分支导出为线性步骤。

候选结果主合同见 result-contract.md；详细技术地图可作为附表，附表中的引用仍要能回到同一证据索引。只有 URL 清单时不得命名为完整调用链图。

## 交付前复核

- 每个“实际发生”是否真有运行证据，而不是静态字符串。
- 权限/状态业务含义有没有被擅自翻译。
- 风险建议有没有错误变成通过/失败结论。
- 附件是否混入认证凭据或无关批量业务记录；已授权且分析必需的业务原值和截图可以保留。
- 标为未覆盖的页面是否又出现在正常 visited 地图里。
