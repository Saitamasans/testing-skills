# 测试视角需求澄清 Skill（开测前需求补全分析）

## 1. Skill 定位

本 Skill 只做需求澄清，不生成正式测试用例，不生成测试点表，不生成需求追踪矩阵，不生成接口测试用例，也不替产品补规则。

默认交付四部分：

1. 会话中的开测准入总结。
2. 会话中的轻量产品核对表。
3. 可直接复制给产品的问题文本。
4. 可下载、可编辑的需求澄清 Excel。

如果用户明确只要口头澄清且不要文件，可以不执行 renderer；只要用户提到文件、Excel、xlsx、留档、发产品或复审，就必须先读取 `references/output-contract.md`，再按结构化 JSON -> schema 校验 -> renderer -> 回读校验的顺序执行。

## 2. 硬规则与边界

1. 本 Skill 只做需求澄清，不生成测试用例。
2. 不输出正式测试点表。
3. 不输出需求追踪矩阵。
4. 不输出接口测试用例。
5. 不把合理假设当作已确认规则。
6. 不替产品编造金额、数量、时间、权限、状态、提示文案或业务规则。
7. 只要仍有 P0 未关闭，就必须标记为 `P0 ⛔ BLOCKING`，不得进入正式用例生成。
8. `P0 ⛔ BLOCKING` 是固定字面量，不能改写。

## 2.1 问题生成门禁

生成产品核对问题前，必须先做一次反误报过滤，目标是减少产品沟通成本，而不是把所有测试联想都抛给产品。

1. 先把需求拆成四类：已明确、真实冲突、真实缺口、低价值边界；只有真实冲突和真实缺口才能进入产品问题。
2. 对已明确内容，按原文或字段上下文自然执行，不要再追问“是否按此执行”。
3. 不要把测试人员可自行设计的边界值、异常态、展示细节默认写成产品问题；除非不确认就会改变核心统计结果、主流程预期或验收结论。
4. 如果同一需求明确给出多个字段或指标各自的定义、阈值、分母或计算对象，默认按字段分别适用；不要把不同指标之间的差异本身当成冲突。只有同一字段内部自相矛盾，或明确要求多个字段共用同一口径但材料冲突时，才提问。
5. 如果需求已经说明时间范围的起止边界、包含关系或截断规则，按原文整体执行，不要把可由区间定义直接推出的边界拆成多个问题；只有规则缺失、互相矛盾或不同理解会产生核心结果差异时，才追问。
6. 如果需求已经明确输入约束、去重口径、条件关系、排除范围或其他可执行规则，直接整理为已明确内容，不要再做同义确认。
7. 如果需求明确指定可复用的现有字段、接口、系统口径或技术资料，且该来源可访问并被确认是本次依据，可以列为资料核对事项；不能因为“可能复用”就跳过产品澄清，也不能把现有实现自动视为需求规则。
8. 宁可少问但问准：默认只输出会影响开测决策或核心验收的高价值问题；低价值问题除非用户要求“穷尽澄清”，否则不进入 Excel。
9. 降噪规则不得覆盖核心风险：只要不同理解会改变主流程、核心业务结果、数据归属、权限或安全边界、状态流转、前后端契约或验收结论，即使看起来像边界问题，也必须保留为澄清问题。
10. 如果多个字段共享同一业务事件、对象、归属关系或数据源，而材料没有说明它们是否共享口径且会影响结果，仍需提出一个合并后的核心问题；不要因为字段名称不同就强行判定为独立。

## 3. 准入结论

每次分析都先给出准入结论：

| 结论 | 含义 | 后续处理 |
|---|---|---|
| 可开测 | 核心流程、规则、边界、权限、异常、验收基本明确 | 可交给独立用例 Skill |
| 有条件开测 | 主流程明确，但仍有 P1/P2 风险未确认 | 可以推进，但要保留风险 |
| 不建议开测 | 存在 P0 缺口，不确认就会基于猜测写用例 | 先让产品回答问题 |
| 不可开测 | 目标矛盾、流程断裂、预期不可验证 | 需求需要先重打磨 |

判断原则只有一个：不确认就无法判断主流程、核心规则、核心预期或最终数据结果的，才算 P0。

准入判断前必须复核：这些 P0 是否真的无法从原文、截图、字段定义、已有系统口径或用户补充中得到可执行结论；如果只是实现细节、异常兜底、文案或边界断言，不得升为 P0。

## 4. 需求澄清维度

重点看这些方面：

| 维度 | 要检查的问题 |
|---|---|
| 业务目标 | 需求想解决什么问题 |
| 使用角色 | 谁能看、谁能操作 |
| 入口路径 | 从哪个页面、按钮、链接进入 |
| 操作对象 | 操作的是谁、哪条数据、哪个资源 |
| 主流程 | 从开始到完成是否闭环 |
| 成功结果 | 成功后页面、状态、数据如何变化 |
| 失败结果 | 失败时如何提示、是否回退 |
| 权限归属 | 是否区分本人、他人、管理员 |
| 状态流转 | 初始、处理中、终态、非法态是否明确 |
| 前后端一致性 | 前端限制后端是否也校验 |
| 数据一致性 | 列表、详情、统计、导出是否一致 |
| 本轮范围 | 哪些纳入，哪些不纳入 |

## 5. P0 / P1 / P2

| 优先级 | 含义 | 是否阻断 |
|---|---|---|
| P0 | 不确认就无法判断主流程、核心规则、核心预期或数据结果 | 阻断 |
| P1 | 影响异常、边界、权限、数据一致性、幂等、并发、前后端一致性 | 通常不阻断，但必须提示 |
| P2 | 影响文案、样式、低风险展示、体验细节 | 不阻断 |

优先级过滤规则：

1. P0 必须满足“答案不同会改变主流程、核心业务结果、数据归属、权限或安全边界，且当前材料没有可执行口径”。
2. P1 必须满足“未确认会造成明显返工、验收争议、数据一致性风险、权限或安全风险，或导致异常行为差异，但主流程仍可判断”。如果测试人员可以依据已明确规则自行覆盖，或来源已被确认且仅需资料核对，不写入产品问题。
3. P2 默认不进入产品核对问题表；只有用户要求完整留档，或该细节已经被原型/需求明确强调时才保留。
4. 同一个业务缺口只问一次；不要把一个口径拆成多个相邻问题，也不要把同义词差异拆成问题。

## 6. 输出流程

读取需求 -> 判断准入 -> 整理已明确内容 -> 形成问题 -> 生成 `clarification-report.json` -> 读取 `schemas/clarification-report.schema.json` 校验 -> 调用 `scripts/render-clarification-assets.mjs` 生成 Excel -> 回读校验 -> 输出会话总结、轻表、可复制文本和下载链接。

## 7. 复审规则

产品回答后要重新复审：

1. 将已回答内容写入“已明确内容”。
2. 检查是否仍有 P0 未关闭。
3. 检查回答是否含糊、冲突、引出新边界。
4. 继续追问尚未确认的核心规则。
5. 只有所有 P0 关闭后，才允许把结论切到可开测。

## 8. 互斥路由与组合调用

本 Skill 走互斥路由；用户确认前最多一个辅助 Skill，并且必须先说明分工。用户要正式测试设计或用例时，应重新路由到独立用例 Skill；本 Skill 永远不生成测试用例。

## 9. 最终自检

输出前检查：

1. 是否明确本 Skill 只做需求澄清，没有生成测试用例。
2. 是否给出开测准入结论。
3. 是否区分 P0、P1、P2。
4. 是否在 P0 未确认时停止进入用例生成。
5. 是否输出已明确内容、本轮不纳入和产品核对问题。
6. 是否保留 `P0 ⛔ BLOCKING`。
7. 是否完成最终自检。
