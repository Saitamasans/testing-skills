# 报告模板

默认输出应包含聊天摘要和离线 HTML 报告两部分。聊天摘要负责让用户快速知道结果；HTML 报告负责归档完整证据。

## 报告元信息表

| 任务名称 | 来源用例包标识 | 测试环境 | 目标地址 | 执行方式 | 执行日期 | 执行角色 | 用例总数 | 通过 | 不通过 | 待定 | 阻塞 | 关键结论 |
|---|---|---|---|---|---|---|---|---|---|---|---|---|

## 逐用例执行表

| 用例 ID | 用例标题 | 前置条件摘要 | 关键步骤摘要 | 预期结果摘要 | 实际结果摘要 | 执行状态 | 证据编号 | 阻塞/待定原因 | 备注 |
|---|---|---|---|---|---|---|---|---|---|

## 问题与风险表

| 问题 ID | 用例 ID | 问题类型 | 严重级别 | 问题描述 | 影响范围 | 建议处理方式 | 是否阻塞 |
|---|---|---|---|---|---|---|---|

## 证据索引表

| 证据 ID | 对应用例 ID | 步骤/节点 | 证据类型 | 文件/位置 | 说明 |
|---|---|---|---|---|---|

| 总体结论 | 覆盖范围说明 | 主要风险 | 待确认项 | 下一步建议 |
|---|---|---|---|---|

## HTML 报告结构

HTML 报告固定包含：

1. 顶部验收结论横幅
2. 测试概览统计卡片
3. 本轮已验证关键点
4. 已执行用例与结果表
5. 阻塞/待定/不通过项说明
6. 关键截图证据区
7. 最终验收结论

HTML 必须是单文件离线报告；可以引用同目录或相对路径截图，但不得请求外部网络资源。

## 结果 JSON 输入契约

`scripts/render-acceptance-report.mjs` 读取的结果文件必须满足以下契约。

必填字段：

| 字段 | 类型 | 说明 |
|---|---|---|
| `taskName` | string | 任务名 |
| `source` | string | 来源用例包 |
| `environment` | string | 测试环境 |
| `executionMethod` | string | 执行方式 |
| `executedAt` | string | ISO 时间或可读执行时间 |
| `totalCases` | number | 用例总数 |
| `pass` | number | 通过数 |
| `fail` | number | 不通过数 |
| `pending` | number | 待定数 |
| `blocked` | number | 阻塞数 |
| `results` | array | 已实际执行的用例结果 |

可选字段：

| 字段 | 类型 | 说明 |
|---|---|---|
| `blockedCases` | array | 未触达执行点的阻塞用例 |
| `evidences` | array | 截图或证据索引 |
| `keyFindings` | array | 聊天和报告中展示的已验证关键点 |

推荐结构：

```json
{
  "taskName": "任务名",
  "source": "来源用例包",
  "environment": "测试环境",
  "executionMethod": "执行方式",
  "executedAt": "ISO 时间",
  "totalCases": 0,
  "pass": 0,
  "fail": 0,
  "pending": 0,
  "blocked": 0,
  "results": [
    {
      "caseId": "用例ID",
      "title": "用例标题",
      "status": "通过|不通过|待定",
      "actual": "实际结果摘要",
      "evidenceId": "证据ID",
      "reason": "阻塞/失败原因"
    }
  ],
  "blockedCases": [
    {
      "caseId": "阻塞用例ID",
      "title": "阻塞用例标题",
      "status": "阻塞",
      "actual": "未触达执行点",
      "evidenceId": "",
      "reason": "阻塞原因"
    }
  ],
  "evidences": [
    {
      "evidenceId": "证据ID",
      "caseId": "用例ID",
      "node": "步骤/节点",
      "type": "PNG截图",
      "file": "相对路径文件名.png",
      "desc": "说明"
    }
  ],
  "keyFindings": [
    "可读的已验证关键点"
  ]
}
```

规则：

- `results` 只放已实际执行的用例。
- `blockedCases` 只放因为前置条件或外部依赖而未触达的用例。
- `pending` 表示已执行但口径未完全定死的结果；`blocked` 表示根本没法执行。
- `status` 只允许使用 `通过`、`不通过`、`待定`、`阻塞`。
- `evidenceId` 必须和 `evidences` 一一对应。
- 脚本必须在缺必填字段、类型错误、状态非法或统计不一致时直接失败，不允许默默补 0 生成假报告。

## 聊天回复模板

最终聊天回复固定按以下顺序输出，不要把完整报告正文塞进聊天：

1. 标题：`验收完成 ✅`、`补充验证完成 ✅ 10/10 全部通过`、`验收完成 ⚠️ 存在待确认项` 或 `验收完成 ❌ 存在不通过项`
2. 范围：`需求 #编号 【优先级】 需求名称 已在测试服完成验收，报告已生成。`
3. 统计：`📊 测试结果：7/10 通过，3 待确认，0 不通过`
4. 状态表：固定三列 `状态 / 数量 / 说明`
5. `🔑 已验证的关键点`：3 到 6 条，写成业务可读事实，不堆技术细节
6. `⚠️ 上线前建议补充验证` 或 `关键发现`：列出待确认、阻塞、风险或执行中发现的注意事项
7. 报告：`报告文件和 N 张截图已生成，可以直接查看。`

聊天回复可以带少量状态 emoji，但正文必须保持专业、直接、可复核。

不要在最终聊天回复里主动插入报告预览截图。HTML 报告本身才是交付物，预览截图只用于执行者自检。
