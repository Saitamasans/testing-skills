# 两阶段导航建图验收场景

## 目标

验证导航建图能够更早进入业务探索，并通过批量结构提取减少模型往返，同时保持当前账号可见导航的完整性和未识别边界。

## 场景 A：大型手风琴后台

页面线索：十多个一级组、数百个二三级入口，同一时间只展开一个菜单组。

期望：

- B01 快速地图先识别直接入口、完整一级骨架、账号上下文、系统形态、可见风险域和当前可见叶子入口。
- 快速地图完成后立即输出初始批次目录，并进入首个高价值业务批次。
- B01-N 完整导航台账进入当前计划，不因先测业务页面而消失。
- 使用批量结构提取形成导航树；只对懒加载、虚拟滚动、动态子级和提取缺口逐组交互。
- 不在每展开一个菜单组后分别保存完整快照或截图。

## 场景 B：小型系统

页面线索：少量入口，结构一次快照即可完整识别。

期望：B01 快速地图与完整台账自然合并，不为遵守两阶段规则制造额外批次。

## 场景 C：懒加载或虚拟滚动菜单

页面线索：子级只有展开或滚动后才进入 DOM。

期望：先批量提取已加载结构，再针对缺口展开或滚动并增量提取；无法可靠识别的范围记录原因，不默认子级不存在。

## 场景 D：非菜单型系统

页面线索：看板、地图、流程画布、监控面板或工作区卡片。

期望：快速地图使用工作区、图层、节点、卡片、钻取入口等价建图；不强行查找侧边栏菜单。

## 场景 E：全功能面处置

现状：用户要求所有页面最终都获得明确状态。

期望：快速地图只负责尽快建立初始计划；完整导航台账仍属于总计划，未识别或未处置入口不得因本轮预算结束而消失。

## 通用验收

- 批量结构提取优先使用 scoped snapshot、语义树和只读 DOM 状态；交互只负责展开、滚动或补缺。
- 不使用主动接口、猜测路由或 `browser_run_code_unsafe` 建图。
- 结构提取结果至少保留名称、层级、父入口、入口类型、目标/定位、展开状态和当前处置状态。
- 批量结果通过总量、父子关系、可展开节点和少量代表入口进行完整性核对。
- 快速地图不能冒充完整台账；完整台账也不能阻塞首个有价值业务页面过久。
