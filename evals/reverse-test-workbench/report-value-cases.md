# 报告价值内核验收场景

## 目标

验证过程小结和测试资产表能够帮助测试、产品和开发做下一步决策，而不是只证明 AI 执行过页面操作。

## 场景 A：只有初始侦察

现状：仅完成登录、导航建账和一次普通查询/重置，没有形成业务规则、异常、关联关系或高价值阻塞。

期望：

- 标题和结论明确定位为 Plugin 验证、初始侦察或低信息增量阶段结果。
- 直接说明本轮不能判断系统质量。
- 不把“确认缺陷 0 个”表达成系统正常。
- 给出最值得继续验证的未知和原因。

## 场景 B：形成有价值规则

现状：通过查询、详情、刷新或关联记录，形成一条有证据的规则或关系。

期望：高价值发现至少表达观察事实、测试判断、证据依据、影响范围、结论强度和建议动作；读者无需翻阅完整操作过程也能理解其价值。

## 场景 C：发现疑似问题但证据不足

现状：页面表现异常，但没有可靠预期或第二证据。

期望：明确写成异常线索、疑似问题、风险或待确认，说明为什么不能升级为缺陷，以及下一步需要什么证据。

## 场景 D：导航清单很大

现状：识别数百个菜单入口，但只有效探索少量页面。

期望：综合结论只使用导航数据说明范围和未覆盖边界；完整菜单、字段、按钮和截图索引留在 Excel/evidence，不占据报告主体。

## 场景 E：形成明确阻塞

现状：核心未知需要其他角色账号、测试数据或 L3 操作，当前无法继续。

期望：把阻塞作为减少不确定性的结果，说明阻塞影响的结论、解除条件、责任方向和恢复后的第一动作。

## 通用验收

- 结论摘要出现在批次过程之前。
- 首先回答：本轮定位、已回答问题、未回答问题、关键新认知、主要风险/问题、建议动作和结论边界。
- 高价值发现使用“事实 -> 判断 -> 依据 -> 影响 -> 行动”的完整链条。
- 报告区分确认缺陷、疑似问题、风险、待确认、阻塞和工具阻塞。
- 导航数量、字段按钮数量、截图数量和批次完成率只能支撑边界，不能替代结论。
- 读者能够在不阅读逐步操作流水的情况下判断本轮价值和下一步优先级。
