# reverse-test-workbench Skill 审计报告

审计日期：2026-08-15

审计对象：`plugins/reverse-test-workbench`

## 当前状态（优先阅读）

**结论：通过，可作为当前发布候选版本使用。**

当前源码与已安装 Plugin 版本：`0.1.0+codex.20260815094916`

当前已验证：

- Skill 结构、触发描述、引用组织和渐进加载规则通过审计。
- 官方 Playwright MCP 能力门禁、登录、快速地图和代表页到达通过验证。
- 任务级计时、`closeout_at` 动作前预算门禁和硬截止记录通过验证。
- `init_run_data.py` 可生成规范事实源，减少模型手写结构和收口试错。
- DOCX、XLSX、`_run-state.json`、构建清单与事实源指纹一致性通过验证。
- 四次独立前向复跑均保持只读边界，没有执行业务写入。

当前唯一环境限制：本机没有 LibreOffice，DOCX 只能完成结构检查，不能完成 Word 页面渲染视觉检查。这是验证能力限制，不是 Skill 运行缺陷。

下文的 P1/P2 内容是**历史审计发现与修复过程**，不是当前仍未处理的问题。

## 优点

1. 入口纪律明确。精确 URL 默认直接新开 Playwright 页面，页面类型判定前禁止标签扫描、产物准备、空命令和无目标工具切换，直接针对历史实跑中最严重的耗时问题。
2. 探索秩序与自由度平衡。菜单是默认骨架，可信主流程可以动态插入，异常随页面穿插，待办池和批次预算限制扩张，动态路径结束后返回导航游标。
3. 覆盖口径诚实。入口识别、页面到达、初步探索、有效探索和路径闭环分开统计；计划批次完成不暗示系统全量完成。
4. 测试价值门禁完整。批次必须回答新理解、证据、影响和后续决策价值，普通查询成功、字段按钮抄录和菜单数量不能冒充有效探索。
5. 产物工程已经确定性化。`run-data.json` 是单一事实源，固定生成器支持校验、部分降级、事务发布、失败回滚、数据指纹去重和受控暂存清理。

## 审计发现与修复

### P1：派生状态与事实源存在两处冲突

- 位置：原 `SKILL.md` 的停止与默认产物章节。
- 问题：仍写成直接保存或维护 `_run-state.json`，与 `run-data.json` 单一事实源冲突。
- 修复：恢复信息统一写入 `run-data.json` 的恢复区，`_run-state.json` 只由固定生成器派生。

### P1：主 Skill 接近上下文上限

- 位置：原 `SKILL.md` 395 行。
- 问题：四维覆盖判定和调度细则与 `exploration-design.md` 存在重复，每次触发都会加载。
- 修复：保留硬判定、关键术语和禁止口径，将详细启发留在 reference；主文件降至 354 行。

### P2：长 reference 缺少目录

- 位置：`browser-execution.md`、`execution-environment.md`、`run-data-contract.md`。
- 问题：超过 100 行但缺少目录，不利于按需定位和局部加载。
- 修复：三个文件均增加一级目录；当前所有长 reference 均有目录。

### P2：JSON Schema 能力表述过满

- 位置：`run-data-contract.md`。
- 问题：原文称 Schema 是“完整机器约束”，但完整字段和敏感信息约束实际由 Python 校验器执行。
- 修复：改为 Schema 提供顶层机器结构，`validate_run_data.py` 提供完整可执行约束。

## 第一次独立前向复跑增量发现

独立 projectless 任务使用 `0.1.0+codex.20260815075610` 完成登录、快速地图和用户列表有效探索。入口导航实际约 1.4 秒，首次业务交互约 108 秒，证明极速入场和“快速地图后先进入业务页面”已经生效；用户列表形成查询边界、重置恢复、跨页面总量和旧/新版刷新关系，不再停留在 UI 抄录。

复跑同时暴露两处发布前缺口：

### P1：执行器嵌套字段未形成机器契约

- 现场：真实 `run-data.json` 使用 `executor_protocol`、`executor_version`，而生成器读取 `protocol`、`version`，导致 `_run-state.json` 两字段为 `null`。
- 根因：fixture 和生成器已有规范字段，但 Schema、契约和校验器只检查 `executor` 对象存在，没有检查内部字段。
- 修复：Schema、契约和校验器统一要求规范执行器字段；生成器回归测试核对派生状态协议和版本；非规范别名输入必须被拒绝。

### P1：运行预算和总耗时口径不闭环

- 现场：报告写约 18 分 38 秒，真实任务墙钟约 26 分 26 秒；前置 Skill 定位和最终收口未计入，并且 15 分钟预算需要外部提醒才停止新增探索。
- 根因：规则要求记录预算和阶段耗时，但未明确任务级起点、预算截止点、自适应收口预留和到点自动停止；事实源也在收口阶段集中拼装。
- 修复：任务级总计时从第一项实际工作开始，覆盖必要 Skill 定位、门禁、探索、模型编排和产物收口；预算形成截止点并预留收口时间，到点自主停止新增探索；B00/B01 后立即建立最小事实源并按批次增量更新。校验器要求完整阶段键，并校验 `total` 包含执行器门禁和产物校验。

以上修复完成后需要再次更新 cachebuster、重新安装并做第二次干净复跑，才能形成最终发布结论。

## 第二次独立前向复跑增量发现

第二次 projectless 任务验证了两个修复点：进入 B00/B01 后即创建最小 `run-data.json`，不再等到收口首次拼装；规范 `executor.protocol/version` 能正确派生到 `_run-state.json`，不再出现空值。

该复跑仍发现一个 P1 预算执行漏洞：任务已经记录端到端截止时间 `2026-08-15T16:54:13+08:00`，但截止后仍调用新的 `browser_click`。这说明“到点停止”作为批次级提醒仍不足以约束工具动作。

### P1：预算有记录但缺少动作前阻断

- 根因：没有单独记录早于硬截止的收口阈值，也没有要求在新批次、动态路径和新页面动作前重新检查预算状态。
- 修复：新增必填 `run.budget_control`，记录 `started_at`、`closeout_at`、`deadline_at`、`last_checked_at`、状态和超时量；校验器强制 `started_at <= closeout_at <= deadline_at`，断点投影保留预算控制状态。
- 行为门禁：每次启动新业务批次、动态插入路径或新页面动作前检查最近可靠时间；进入 `closeout_at` 后禁止新的点击、导航、输入和范围扩张，只允许事实源、固定产物、校验和页面保留确认。

该动作前门禁已通过静态规则、Schema、校验器、生成器和生命周期回归测试；部署后仍需一次短预算独立复跑验证自主停止。

## 第三次短预算前向复跑增量发现

第三次 projectless 任务使用 `0.1.0+codex.20260815091430`，在 `closeout_at` 前停止了所有浏览器扩张；最后浏览器动作发生在阈值前，之后没有新的点击、导航或输入。动作前预算门禁因此验证通过。

端到端硬预算仍未通过：固定生成器本身不到 1 秒，但模型在收口阶段用约 8 分钟手写和反复修正 18KB `run-data.json`，包括运行定位数组、探索重点数组、导航/页面 ID、预算状态枚举和关键发现对象形状。总耗时 12 分 40.839 秒，超出 8 分钟预算 4 分 40.839 秒。

### P1：事实源结构仍依赖模型从空白手写

- 根因：Skill 虽要求增量事实源，但 Plugin 没有提供可直接创建的规范骨架；Schema 只覆盖顶层和部分嵌套字段，模型需要猜测大量展示与生成器契约。
- 修复：新增跨平台 `scripts/init_run_data.py`，确定性生成执行器、预算、阶段时间、续跑、覆盖和全部顶层集合；AI只增量写现场事实，不再手写基础结构。
- 校验收紧：`summary.key_findings` 必须使用事实、判断、依据、影响、动作和置信度对象，不能用字符串列表绕过后再由生成器报错。
- 收口策略：短预算默认预留至少 3 分钟或总预算 30% 中较大者；首次完整生成失败只允许一次集中修正，仍失败立即部分交付，不以多轮字段试错突破硬截止。

初始化器、校验器、生成器、价值规则、生命周期、Skill 和 Plugin 校验通过后，需更新 cachebuster 并做最后一次预算专项复跑。

## 第四次初始化器前向复跑与最终一致性门禁

第四次 projectless 任务使用 `0.1.0+codex.20260815093521`，实际调用 `scripts/init_run_data.py`，没有手写顶层骨架或发生字段修正轮次。端到端耗时 6 分 18.221 秒，在 7 分钟硬截止前约 41.8 秒完成；最后浏览器动作早于 `closeout_at`，阈值后浏览器扩张为 0。任务主动降低为“执行器/Plugin 验证 + 初始侦察”，没有因产物齐全或代表页到达而升级结论。

外部复核发现任务在派生产物发布后又更新了最终耗时，导致最新 `run-data.json` 与构建清单指纹不一致。该问题未被任务自己的校验发现。

### P1：发布后事实源变化会使派生产物静默过期

- 修复：新增只读 `scripts/check_artifact_consistency.py`，按生成器相同的规范化 JSON 指纹比较最新事实源与构建清单，并核对 `_run-state.json` 的运行 ID、执行器协议、执行器版本和预算控制状态。
- 生命周期门禁：成功发布后禁止再修改 `run-data.json`；最终事实必须变化时，只允许更新后重建一次并重新检查指纹。
- 现场验证：第四次真实复跑产物在修改后被检查器准确判定为 `stale`；调用固定生成器重建后，检查器返回 `consistent`。

当前源码已经完成完整 Skill 审计、四次独立前向复跑驱动的修复、确定性初始化、预算动作门禁、固定产物生成和最终事实指纹校验。浏览器探索速度、测试价值、覆盖诚实度、短预算自主收口和派生产物一致性均获得实际证据。
